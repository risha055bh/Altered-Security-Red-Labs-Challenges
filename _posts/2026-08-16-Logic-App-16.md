Category: Cloud Security | Platform: Microsoft Azure | Severity: Critical Difficulty: Easy | Attempts: 19 | Lab Duration: 30 min

Scenario

In certain scenarios, the compromised user might own the Logic App or have permission to read the workflow of the Logic App. This can reveal sensitive data hardcoded in the workflow template. Abuse the user permissions and obtain the flag.

Overview

What is a Logic App workflow? A Logic App workflow is a visual representation and implementation of a business process or integration scenario in Azure Logic Apps. It defines the steps, actions, and conditions that are executed in a specific sequence to automate a particular workflow.

Impact

Sometimes sensitive data could be hard-coded into code or template files which could be leaked.
Any identity with Reader access on a Logic App can view its full workflow definition, including any parameters, connection strings, API keys, or secrets that were hardcoded instead of using secure parameters or Key Vault references.
Because Logic App definitions are stored as plain JSON (ARM templates), secrets embedded in them are also exposed through deployment history, ARM template exports, and source control if the workflow was ever committed to a repo.

Why It's Important to Secure

Logic App workflows are often built quickly to automate business processes, and developers frequently hardcode connection strings, API keys, tokens, or credentials directly into the workflow JSON for convenience. Because Logic App definitions are readable by anyone with Reader-level access — not just Owner or Contributor — this significantly widens the exposure window. A single overly-permissive role assignment can leak credentials that grant access to entirely separate systems (databases, storage accounts, third-party SaaS APIs), turning a low-privilege read permission into a much larger compromise.

Impact in a Real-Time Environment

In a production environment, this misconfiguration can lead to:

Lateral movement — leaked credentials or connection strings can be reused to pivot into other Azure resources or external services (e.g., a database, storage account, or third-party API).

Data exfiltration — if the hardcoded secret grants access to a data store, an attacker can extract sensitive business or customer data.

Persistence — an attacker with Contributor rights could modify the workflow to add a backdoor action (e.g., forwarding data to an external endpoint) without triggering obvious alerts.

Blast radius beyond Azure — many Logic Apps integrate with SaaS platforms (Slack, Salesforce, SendGrid, etc.); hardcoded API keys for these services extend the compromise outside the Azure tenant entirely.

Remediation

Never hardcode secrets in Logic App workflow definitions. Use Azure Key Vault integration or secure parameters instead.

Use managed identities for Logic App connections wherever possible, instead of embedding static credentials.

Apply least privilege — restrict Reader/Contributor access on Logic Apps to only the users and service principals that genuinely need it.

Regularly audit Logic App definitions (via code view or ARM export) for hardcoded secrets, using tools like git-secrets, TruffleHog, or Azure's built-in secret scanning if the templates are stored in a repo.

Enable Azure Policy to flag or block deployments of Logic Apps containing plaintext secrets in parameters.

Rotate any credentials that were ever hardcoded, even after remediation, since they may already be cached in deployment history or logs.
How This Helps During Incident Response

Faster root-cause identification — knowing that Logic App workflows can contain hardcoded secrets gives responders a quick pivot point when investigating how an attacker obtained credentials for an unrelated resource.

Scoped containment — if a Logic App is found to expose a secret, IR teams can immediately rotate that specific credential and check Azure Activity Logs for any resource accessed using it, rather than assuming a broader compromise.

Better detection engineering — this pattern highlights the value of alerting on Reader-level access to Logic App code view or ARM template export actions, which are often overlooked in favor of monitoring Owner/Contributor activity.

Improves playbooks — incident responders can build a checklist step to always review Logic App JSON definitions for hardcoded secrets as part of any Azure compromise investigation, not just as an afterthought.
